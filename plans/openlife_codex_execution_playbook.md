# OpenLife Codex 执行手册

> 适用场景：你通过 Codex 持续 coding 推进 OpenLife
> 目标：让每一轮开发都能稳定推进，而不是在大 PRD 里反复发散

---

## 1. 文档定位

这不是愿景文档，也不是产品宣传文案。

这份文档只回答四个问题：

1. Codex 每一轮应该优先做什么
2. 一次任务应该切多大
3. 做完之后要如何验证
4. 哪些改动必须同步回文档

与其他文档的关系：

- 长期目标和产品哲学：见 [OpenLife_Final_PRD.md](/Users/fujing/Desktop/偶来福/OpenLife_Final_PRD.md)

## 2. 当前目标

当前阶段，OpenLife 的目标已经从“做出 Alpha 底座”进一步切换到：

- 把现有 Alpha 收口成 **可稳定试用版本**
- 让用户可以自己走完 `设置 → 构建 → 对话 → 仪表盘 → 校准/回滚`
- 为接下来的“边试用边修改”建立一条可重复验证的主基线

当前版本优先围绕五个闭环推进：

1. 对话闭环
2. 人生模型闭环
3. 校准/进化闭环
4. 工具审批/执行闭环
5. 恢复/治理闭环

如果一项需求不能明显强化这五个闭环，就默认不进入当前迭代。

### 2.1 当前执行侧重点

当前更适合 Codex 做的，不是继续铺大功能，而是：

- 收口跨页面说明
- 补试用主链路中的断点
- 强化错误可见性和恢复路径
- 建立更真实的 smoke 验证

当前不建议优先做的：

- 再开远期产品线
- 大规模重构为“更优雅的架构”
- 脱离试用主链新增复杂生态能力

## 3. Codex 工作模式

### 3.1 单轮任务大小

Codex 单轮最适合处理以下粒度的任务：

- 1 个明确 bug
- 1 条完整但不跨太多模块的主链路
- 1 个页面 + 1 个对应后端接口
- 1 个核心模型结构升级 + 必要迁移
- 1 组相关测试补齐

不建议一次性让 Codex 同时做：

- 大规模架构重写
- 多个 Phase 并行推进
- 同时改 PRD、架构、前后端、测试、视觉重设计

### 3.2 每轮标准节奏

每轮开发尽量遵循这个顺序：

1. 读相关代码和现有文档
2. 判断任务归属哪个闭环
3. 先补或修正契约，再改实现
4. 实现最小可用闭环
5. 跑测试或补测试
6. 更新文档中的状态或执行说明

### 3.3 单轮输出要求

每一轮结束时，Codex 至少要明确给出：

- 改了什么
- 哪些文件被修改
- 怎么验证
- 还有什么没做
- 是否需要同步更新计划文档

## 4. 优先级规则

所有需求按下面顺序竞争优先级：

### P0：主链路稳定性

包括：

- 聊天状态一致性
- 前后端契约一致性
- 会话/模型/记忆持久化
- 高风险工具审批流
- 错误处理和回退路径

### P1：人生模型真实可用

包括：

- Builder 真正产出结构化模型
- LifeModel schema 与 UI 对齐
- 四维关联分析开始可用
- Dashboard 不只是展示，而是真能指导下一步

### P2：长期陪伴能力

包括：

- 记忆检索质量
- 周期校准
- 微进化建议
- 版本快照和回滚体验

### P3：生态扩展

包括：

- MCP 模板
- A2A 桥接
- 工具推荐
- 更复杂的多 Agent 协作

### P4：远期叙事

包括：

- 数字遗产
- 联邦网络
- 多端同步
- 插件市场

当前阶段默认不主动进入 P4。

## 5. 任务切分模板

当你要让 Codex 开始一个新任务时，尽量按这个格式描述：

```md
目标：
影响闭环：
涉及文件：
预期结果：
验证方式：
非目标：
```

示例：

```md
目标：让 Builder 产生的身份/目标字段完整写入 LifeModel
影响闭环：人生模型闭环
涉及文件：openlife-core/src/builder.rs, openlife-core/src/life_model.rs, frontend/src/pages/BuilderPage.tsx
预期结果：完成构建后，Editor 和 Dashboard 都能读到新字段
验证方式：cargo test + frontend vitest + 手动跑一次 Builder 流程
非目标：不在本轮做校准或版本快照优化
```

## 6. 代码级执行规则

### 6.1 先改契约，再改页面

如果一个功能横跨 Tauri command 和 React 页面，优先顺序必须是：

1. 数据结构
2. 后端返回值
3. 前端类型
4. 页面状态和交互
5. 测试

### 6.2 避免双轨逻辑继续膨胀

以下领域如果出现两套实现，优先做收敛而不是继续复制：

- 流式 / 非流式聊天
- Builder / Editor 对同一模型字段的写入
- MCP 工具执行 / 审批 / 审计
- 快照创建 / 自动快照 / 回滚

### 6.3 对高风险能力使用状态机

以下能力不要用零散布尔值拼出来：

- 工具执行
- 校准确认
- 进化应用
- 导入导出

优先使用明确状态：

- `pending`
- `approved`
- `running`
- `succeeded`
- `failed`
- `rolled_back`

### 6.4 所有新功能都要回答三个问题

Codex 做任何新增功能时，都应显式回答：

1. 数据落在哪里
2. 页面刷新后是否还在
3. 出错时用户能看到什么

如果这三个问题答不清，这个功能还不算完成。

## 7. 测试与验证

### 7.1 最低验证要求

涉及后端逻辑时，至少做下面之一：

- `cargo test -q`
- 新增或更新 Rust 单测

涉及前端交互时，至少做下面之一：

- `npm test -- --run <相关测试>`
- 新增或更新 Vitest 用例

涉及主链路时，优先同时做两边。

### 7.2 当前最该补的测试类型

优先补下面这些，而不是只补渲染测试：

1. 聊天主链路测试
2. 高风险工具确认测试
3. 会话切换与持久化测试
4. Builder 生成模型字段测试
5. 校准确认后快照生成测试

### 7.3 手动验收建议

每完成一个较大的任务，至少手动走一次真实路径：

1. 打开桌面应用
2. 进入对应页面
3. 走一次成功路径
4. 走一次失败路径
5. 刷新/重启后确认状态是否持久

### 7.4 当前推荐 Smoke 基线

在 OpenLife 当前阶段，最有价值的手动 smoke 不是“多测页面”，而是固定走这条：

1. 打开桌面端
2. 进入 `Settings`
3. 完成模型配置或确认模型可用
4. 进入 `Builder`
5. 如果已有 `待确认 Review`，优先点“去审阅”；否则完成一次快速构建
6. 应用 Review 后，确认 `current/life_model.yaml` 已真实变化
7. 进入 `Chat` 发送一条真实消息
8. 进入 `Dashboard` 看是否给出明确下一步与模型依据
9. 进入 `Calibration` 看是否能理解建议来源
10. 进入 `VersionControl` 看是否存在快照/回滚路径
11. 刷新或重启后确认聊天和模型状态仍在

如果这条链路没有跑通，就不要判定“这个版本可以继续扩功能”。

## 8. 文档同步规则

以下情况必须同步文档：

### 8.1 要更新主计划的情况

如果出现下面任一情况，更新 [plans/openlife_development_plan.md](/Users/fujing/Desktop/偶来福/plans/openlife_development_plan.md)：

- 某个 Sprint 已实质完成
- 某项任务被放弃或替换
- 实际优先级发生变化
- 当前阶段目标边界需要调整

### 8.2 要更新 PRD 的情况

只有下面几种情况才改大 PRD：

- 产品边界变化
- 长期路线变化
- 原有愿景不再成立
- 某个高层架构判断被推翻

不建议把每次实现细节都回写进大 PRD。

### 8.3 代码实现与文档冲突时

优先级如下：

1. 当前真实代码行为
2. 当前阶段主计划
3. Codex 执行手册
4. 大 PRD

如果大 PRD 和当前实现明显冲突，先修正文档，不要强行让代码迎合过期叙述。

## 9. 当前推荐路线

如果从今天开始继续推进，建议严格按这个顺序：

### 第一组

- 聊天链路收口
- 前后端 contract 收口
- 工具审批/执行/审计收口

### 第二组

- LifeModel schema 对齐
- Builder 写入链路做透
- Dashboard 围绕“今天/本周该做什么”重组

### 第三组

- 记忆写入与混合检索
- 周期校准
- 微进化建议
- 快照/回滚闭环

### 第四组

- MCP 模板化
- A2A/LayeredReasoner 桥接
- 工具推荐与更复杂生态

## 10. 一句话原则

当前阶段，OpenLife 的开发原则只有一句：

**先把它做成一个稳定、可信、真正理解用户的人生对话系统，再把它扩展成平台。**

OpenLife LifeModel-HS 架构计划

日期：2026-05-27 状态：仅设计的架构计划 范围：下一代 OpenLife LifeModel，作为本地优先、由用户治理的个人启发式系统 源文件：plans/lifemodel_hs_architecture_plan.md

本计划的实现入口已由 plans/adr/0013-lifemodel-hs-source-of-truth-governance.md 和 plans/lifemodel_hs_mvp_task_specs.md 接管。它仍是设计基线，但本身不要求、也不包含生产代码变更、迁移、运行时变更或功能实现。

1. 执行层设计

LifeModel-HS 将当前 LifeModel 从一个主要被物化出来的用户画像，转变为用户拥有的个人启发式系统。

目标 LifeModel 不是一个 YAML 文件，也不是一段自然语言画像。它是一小组持久、类型化的存储和运行时选择器：

  • 原始 Life Data 保留在其来源系统中，例如聊天、记忆、日历、文件、工具轨迹、反馈和 AgentRunEvent。
  • 启发式学习把原始数据转换为规范化的 Life Event、Signal、Evidence、Candidate Heuristic、Candidate State Patch，以及可治理的 Proposal。
  • 已接受的 HS 资产存放在专用存储中：EvidenceStore、HeuristicStore、StateStore、PolicyStore、RegressionSuite 和 AuditLog。
  • 物化视图把选定的已接受资产渲染为当前 OpenLife 界面所需的格式，包括当前 LifeModel YAML、PromptStack 块、UI 摘要和运行时上下文包。
  • AgentRuntime 不再“默认接收整个 LifeModel”。它向 ContextSelector 和 HeuristicSelector 请求字段级、任务级、隐私感知的上下文。
  • 任何高风险的身份、价值观、长期目标或隐私边界都不会被静默改写。HL 可以提出建议；用户负责治理。

核心转变是：

当前：
LifeModel YAML -> 宽泛的 PromptStack 注入 -> Agent 输出 -> Proposal -> LifeModel patch

目标：
Raw Life Data -> Life Event -> Signal -> Evidence -> Candidate Heuristic/State Patch
-> Governance -> Regression -> Accepted HS Asset -> Materialized LifeModel View
-> Context/Heuristic selection -> AgentRuntime behavior

3. 当前事实与目标设计

领域当前事实目标设计
LifeModel 真相来源LifeModel 是序列化为 YAML 的 Rust struct，包含 identity、goals、capabilities、state、relationships、preferences 和 evolution_rules。已接受的 HS 资产成为真相来源；YAML 成为物化出来的兼容视图。
运行时注入PromptStack 可以注入完整 YAML、state hint、evolution hint 或 summary。ContextPolicy 是类别级的。ContextSelector 和 HeuristicSelector 按任务、风险、隐私和 token budget 选择具体状态字段、启发式、证据摘要和策略。
记忆MemoryStore 持久化 messages/memories/snapshots/state history。VectorStore 检索 chunks 并支持 tier/archive 维护。Memory 仍然是原始/检索层。EvidenceStore 是单独的精选层，包含 provenance、negative evidence、confidence、conflict、decay 和 governance status。
证据MemoryEvidence 已存在，并且可以把 evidence 转换为 proposal。它还不是完整持久化的证据图。EvidenceStore 是一等公民：append-only、可查询、感知冲突，并且链接到 events、signals、proposals、heuristics、regressions 和 materialized views。
信号抽取聊天 proposal 抽取使用带 PromptStack 的本地 LLM 和 fallback heuristics。它可以生成 goal、state、capability 和 memory proposals。SignalExtractor 输出类型化 Signals，带 extraction method、confidence、uncertainty、negative cues 和 audit。候选生成不能直接修改 HS。
治理LifeModel、MemoryWrite、MemoryArchive、ToolPermission、外部写入、计划任务、数据导出都有 proposal-first 路径。LifeModelGovernor 使用风险策略、证据阈值、回归结果、冲突检查、批处理和用户审阅疲劳控制来治理候选 HS 资产。
PatchLifeModel patch/risk/snapshot 路径已存在。Patch 仍然是物化视图的应用机制，但已接受的 HS 资产才是规范来源。PatchStore 记录视图物化和兼容性 mutation。
运行时 traceAgentRunEvent 是 append-only，并对运行时转换做 metadata-redacted 处理。HL 和 HS 维护也输出 metadata-safe event，或并行的 HS audit log，并链接到 AgentRunEvent ID。
Legacy evolutionCalibration 默认 proposal-first，但如果结果表示已应用，run_micro_evolution 仍可直接应用；legacy direct calibration 在配置后面。所有 LifeModel-HS mutation 汇聚到 Proposal-first。Direct apply 被移除，或隔离为 dev/test legacy 兼容路径，绝不作为产品路径。
回归还没有持久的 LifeModel regression suite 来覆盖偏好/启发式。RegressionSuite 存储用户批准的场景，并在接受或提升有影响的启发式前运行。
压缩VectorStore 有 tier/archive；LifeModel 没有 HS compression。CompressionEngine 合并重复启发式、削弱过时规则、归档低价值资产，并物化简洁视图。

4. 问题响应矩阵

当前问题设计响应剩余风险新增复杂度
LifeModel 表现得像静态画像/YAML 快照。HS canonical stores 将原始数据、证据、状态、策略、启发式、回归和物化视图分离。早期 MVP 仍可能通过 YAML 渲染。需要维护更多 store 和迁移。
LifeModel 主要通过 PromptStack 注入并由 Agent 消费。ContextSelector 和 HeuristicSelector 成为 PromptStack 装配和工具执行前的运行时网关。Selector 质量决定运行时有用性。需要任务分类和 selection audit。
Agent run 在执行后产生 Proposals，间接更新 LifeModel。HL 在 After Observe 和 Reflect 期间运行，在 Proposal 之前产生有证据支撑的候选资产。长时异步 HL 可能落后于用户预期。需要 job orchestration 和状态 UI。
Memory 主要是检索上下文，而不是完整证据。EvidenceStore 只提升来自 memory/events 的规范化、带 provenance 链接的 claim。一些原始记忆可能永远不会成为 evidence。需要 evidence schema、scoring 和 review。
Signal extraction 有误报、漏报和污染风险。Signals 携带 method、confidence、uncertainty、negative cues、source spans 和 audit；低置信度不会成为 evidence。LLM 和 heuristics 仍会遗漏细微信号。每次抽取需要更多 metadata。
没有可执行启发式、证据链、回归测试、压缩、遗忘、冲突检测。Heuristic schema 包含 triggers、conditions、guidance、risk、evidence、opposing evidence、lifecycle 和 validation state；RegressionSuite、CompressionEngine、MaintenanceEngine 是一等模块。MVP 不能立刻解决所有维护质量问题。启发式 lifecycle 必须保持小而可理解。
注入是宽类别级，不是字段/任务级。Selectors 按 task kind、risk、privacy 和 budget 选择精确的 heuristics/state/policies。仍可能过选或少选。需要 selector diagnostics。
YAML 快照不适合作为长期真相来源。YAML 降级为 Materialized LifeModel View。迁移完成前，现有代码仍消费 YAML。有双写或物化一致性风险。
Legacy micro-evolution/direct-apply 路径并存。迁移让所有 HS 更新通过 LifeModelGovernor 和 ProposalStore。某些 dev/test flags 可能残留。需要源码审计和废弃 gate。
规则膨胀、过时记忆污染、短期状态污染、确认疲劳、prompt 污染。证据阈值、时间衰减、state-vs-identity 边界、proposal 批处理、selector token budgets、compression 和 negative evidence 降低这些风险。用户特定行为仍可能过拟合。维护任务成为产品关键路径。

5. 不可协商的不变量

  1. Raw Life Data 永远不能直接修改 LifeModel-HS。
  2. HL 可以生成候选；只有经治理接受后才会创建已接受的 HS 资产。
  3. 高风险的身份、价值观、使命、长期目标、关系和隐私边界必须经过用户明确确认。
  4. 被拒绝的 proposal 会成为 negative evidence，而不是被丢弃的噪音。
  5. 运行时上下文按任务和策略选择；宽泛的 full-block 注入仅作为兼容路径。
  6. 云模型路径只能接收策略批准的物化摘要。
  7. 每个已接受的 heuristic 都必须能通过 evidence 和 audit lineage 解释。
  8. 每个有影响的 heuristic 在提升前必须具备 regression awareness。
  9. Compression 和 forgetting 不是额外清理工作；它们是正确性的一部分。
  10. UI 必须让用户能检查、编辑、拒绝、回滚、归档并理解 HS 资产。

6. 核心概念定义

概念定义与边界输入输出生命周期与所有权与现有 OpenLife 的关系
LifeModel用户拥有的个人启发式系统：已接受的 state、policy、evidence、heuristics、regression、maintenance rules 和 materialized views。不只是 YAML、画像文本或 prompt 内容。已接受的 HS 资产、materialization policy、用户编辑、已接受的 proposals。Materialized YAML、PromptStack blocks、UI summaries、runtime context packets、selector results。由用户拥有；由 LifeModelGovernor 和 MaintenanceEngine 维护；可版本化、可审计、可回滚。当前 LifeModel struct 成为物化视图和兼容 schema。
Raw Life Data来自对话、文件、工具结果、日历、反馈、状态记录、计划、AgentRunEvents 和外部来源的原始记录。原始数据不能被信任为模型真相。聊天消息、记忆、向量 chunks、工具输出、run events、反馈、用户上传。仅作为 normalization input。由用户拥有；按来源设置 retention 和隐私控制。当前 MemoryStore、VectorStore、AgentRunEvent、feedback、files 和 state_history 是原始来源。
Life Event一个规范化、不可变的事件，描述用户生活或 agent 交互中发生的事。原始记录和 source metadata。带 source refs、time、actor、privacy、payload digest、redacted summary 的类型化 event。Append-only；可以被 supersede，但不被 mutation。把 AgentRunEvent 思路扩展到生活领域事件，但不取代 AgentRunEvent。
Signal从一个或多个 Life Events 中抽取出的潜在有意义模式。Signal 弱于 Evidence。Life Events、source spans、extractor prompts/rules、model outputs。带 confidence、uncertainty、polarity、affected domain 和 extraction audit 的类型化 signal。由 SignalExtractor 创建；被提升、削弱或丢弃。当前 chat extraction 和 MemoryEvidence detection 成为产生 Signal 的步骤。
Evidence关于用户的受支持 claim，带 source lineage、confidence、recency、negative evidence 和 conflict links。Evidence 强于 Signal，但自身仍不是 heuristic。Signals、用户确认、已接受/拒绝的 proposals、run outcomes、重复观察。供 candidate generation、selectors、explanations 和 regression 使用的 evidence record。Append-only versions；confidence 会衰减；可被 opposing、archived 或 superseded。当前 MemoryEvidence 是种子形状，但需要持久化和 graph links。
HeuristicAgent 的可执行指导单元：scope、trigger、condition、guidance、priority、confidence、risk、evidence links、opposing evidence 和 lifecycle state。Evidence clusters、用户撰写的 rules、已接受 proposals、regression outcomes。Runtime guidance、policy constraints、selector candidates、prompt blocks 或 tool constraints。Draft -> proposed -> accepted -> active -> trial -> deprecated/archived；用户治理高风险变更。取代 freeform evolution_rules，成为类型化、可治理、可执行资产。
State用户当前或近期状况、关注点、能量、健康、情绪、义务和临时上下文的时间敏感表示。不是 identity。State events、check-ins、feedback、tool observations、用户编辑。State assets 和 materialized current-state views。默认短 TTL；没有重复 evidence 和确认，不得提升为 identity。当前 state 字段和 state_history 成为物化层与原始层。
Policy治理 privacy、model routing、context selection、tool behavior、confirmation、retention 和 HS maintenance 的规则。用户设置、已接受的 policy proposals、risk classifier、defaults。Runtime decisions、selector constraints、proposal requirements、audit reasons。可版本化并对用户可见；privacy policies 需要明确确认。构建于 PrivacyPolicy、ContextPolicy、ToolRuntime、risk classifier、network policy 之上。
Proposal针对 HS assets、materialized views、memory、tools 或 external actions 的可治理变更请求。Proposal 是风险 mutation 唯一的产品路径。Candidate heuristic/state/policy patches、用户编辑、tool permission requests、memory writes。Pending/accepted/rejected/edited/postponed decision 和可选 apply result。由 Governor 或 tools 创建；由用户或允许的策略解决；拒绝会创建 negative evidence。当前 AgentProposal 和 ProposalStore 仍是核心。
Regression Scenario一个稳定测试用例，用来描述已接受 HS 行为在未来运行中应如何响应。用户批准的示例、被拒绝的不良行为、已接受 proposals、privacy incidents。针对 candidates、selectors、materialized views 和 prompts 的 pass/fail results。从重要决策创建；可版本化；在提升前和维护期间运行。新层，补充现有 unit tests 和 AgentRun replay。
Compression在不丢失 provenance 或 rollback 的前提下，合并、摘要、削弱、归档或遗忘 HS 资产的维护过程。Heuristic clusters、stale evidence、low-use rules、conflicts、negative evidence。Compressed heuristics、archived records、materialized summaries、deletion proposals。定期或用户触发；高风险 compression 需要审阅。基于 VectorStore tier/archive，但应用于 HS assets。
Materialized View为某个特定 consumer 派生出来的已接受 HS 资产表示。它不是规范真相。Accepted assets 加 render policy。YAML LifeModel、prompt blocks、UI cards、route policies、context packets。确定性重建；带 version 和 source asset IDs 缓存。当前 LifeModel YAML 成为 view:lifemodel_yaml@compat。
Personal Heuristic System完整的软件化系统，组织用户拥有的 heuristics、state、policy、evidence、regression、selectors、materialization 和 maintenance。所有已接受的 HS stores 和 governance rules。更好的 Agent behavior、explanations、稳定个人连续性、更安全更新。长期存在；用户拥有；AI 可通过 schema 和 audit 维护。成为下一代 LifeModel 架构。

7. 系统边界

LifeModel-HS 是：

  • 面向个人 heuristics、state、evidence、policy、regression、materialized views 和 maintenance 的本地优先资产系统。
  • 一个运行时决策层，在 ReAct 之前、期间和之后改善 Agent 行为。
  • 一个治理系统，让学习过程可解释、可审阅、可逆，并归用户所有。
  • 一个维护系统，旨在抵抗 memory corruption、rule bloat、prompt pollution 和 stale identity。

LifeModel-HS 不是：

  • 单个 YAML 文件。
  • 向量数据库。
  • Prompt template。
  • 通用的、自主自修改用户身份系统。
  • 隐藏的 personalization cache。
  • LLM、AgentRuntime、MemoryStore、ProposalStore、ToolRuntime 或 PrivacyEngine 的替代品。
邻近系统关系
LLMLLM 可以抽取 signals、摘要 evidence、提出 candidates、解释 conflicts 或运行 regression simulations。它从不拥有 truth，也不会静默写入已接受的 HS assets。
AgentRuntimeRuntime 向 selectors 查询相关 heuristics/state/policy。Runtime 也把 observations 和 outcomes 反写为 Life Events。
ReActHS 参与 Reason、Act、Observe、Reflect、Proposal 和 Replay。它约束 action intensity、tool choice、privacy route 和 explanation style。
MemoryMemory 是原始/检索数据。EvidenceStore 是精选 claim data。Memory 可以支撑 Evidence，但 memory 默认不是 Evidence。
PromptStackPromptStack 将已选 HS assets 渲染为 model-facing blocks。它应接收被选择、版本化、按策略限定范围的 blocks，而不是默认接收宽泛 YAML。
ProposalProposal 是 HS mutation 的治理门。已接受 proposals 创建或更新 HS assets 和 materialized views。拒绝成为 negative evidence。
PatchPatch 应用 materialized view changes 和兼容 LifeModel mutations。Patch 不绕过 HS canonical stores。
ToolRuntimeHS policies 约束 tool availability、confirmation thresholds、action intensity 和 replay。Tool observations 流入 Life Events。
PrivacyPrivacy policy gate extraction、storage、model route、context selection、materialized views、audit payloads 和 retention。
UIUI 是用户的治理驾驶舱：review candidates、inspect evidence、edit heuristics、resolve conflicts、run regressions、rollback、archive，并调节 proposal frequency。

8. 数据拓扑

目标拓扑使用一小组类型化 store。SQLite 是自然的第一实现，因为现有 app 已经使用本地 SQLite 管理 memory、vectors、proposals、patches、events 和 stores。

Raw sources:
  MemoryStore, VectorStore, AgentRunEventStore, FeedbackStore, Calendar/File/Tool traces

HL normalization:
  LifeEventStore -> SignalStore -> EvidenceStore

HS canonical assets:
  HeuristicStore
  StateStore
  PolicyStore
  RegressionSuite
  HS AuditLog

Governance:
  LifeModelGovernor -> ProposalStore -> PatchStore/ViewMaterializer

Runtime:
  ContextSelector + HeuristicSelector -> PromptStack / ToolRuntime / ModelRouter / UI

Materialized views:
  LifeModel YAML compatibility view
  PromptStack HS blocks
  UI summary views
  model-routing policy view

11. HS 内部架构

模块职责数据结构当前关系实现方向风险
LifeEventStore持久化来自 raw sources 的规范化、不可变 life events。LifeEvent、source refs、privacy metadata、digest。扩展 AgentRunEvent 和 MemoryStore，但不合并它们。SQLite table 加 chat、memory、tool、feedback、calibration、user edits 的 source adapters。Event duplication、privacy payload mistakes。

EvidenceStore存储精选的 supported claims 和 opposition。Evidence、conflict links、confidence、recency、status。将当前 MemoryEvidence 演进为持久 graph。SQLite，按 affected_path、evidence_type、status、risk、privacy 建索引。Evidence bloat 和 stale claims。
HeuristicStore存储可执行的个人 heuristics。下方 Heuristic schema、lifecycle、examples、validation。取代 freeform evolution_rules 作为 canonical asset。SQLite 加 JSON columns 存 trigger/condition/guidance；确定性 materialization。Rule bloat、overfitting、conflicts。

LifeModelGovernor候选 HS 变更的主治理编排器。Candidate、Proposal、risk decision、evidence summary、regression report。构建于 ProposalEngine、ProposalStore、risk classifier、PatchStore。创建 Proposals 的新 service；绝不 direct writes。Proposal fatigue；accidental bypass。
HeuristicSelector为任务选择 active heuristics。Query: task, intent, risk, privacy, context budget；Output: ranked heuristics。PromptStack/AgentRuntime 前的新层。确定性 filter + scoring；之后对 heuristic text 做 semantic retrieval。遗漏关键 heuristic；选择太多。
ContextSelector选择 state、evidence summaries、materialized fields 和 memories。带 included/excluded/audit 的 Context packet。用 field-level selection 取代 broad ContextPolicy。用 path-level selectors 和 metadata-only audit 扩展 ContextAssembler。Prompt pollution、privacy leakage。
RegressionSuite存储并运行 behavior/privacy regression scenarios。RegressionScenario、result records。新层；补充 AgentRun replay。从 deterministic scenario checks 和 prompt snapshots 开始；之后做 model simulations。Flaky validation、coverage gaps。

13. ReAct 交互设计

LifeModel-HS 应改善下一次 Agent run，而不只是存储知识。

13.1 Reason 之前

输入：

  • AgentTask、用户消息、privacy policy、可用工具、近期运行上下文。

HS 工作：

  • ContextSelector 识别相关 state fields、已接受 policies、compact evidence summaries 和 memories。
  • HeuristicSelector 按 trigger、task kind、risk、privacy 和 token budget 选择 active heuristics。
  • Materializer 将已选 assets 渲染为 PromptBlocks 或内部 runtime constraints。
  • Audit 记录 included/excluded assets，但不包含原始敏感内容。

运行时效果：

  • 更好的上下文选择、更低 prompt pollution、字段级 privacy、更少过时 profile 注入。

13.2 Act 期间

输入：

  • 拟议工具调用、model route、action intensity、write/external side effect。

HS 工作：

  • PolicyStore 和已选 heuristics 约束 tool choice、confirmation level、model route 和 action intensity。
  • Privacy-sensitive heuristics 可以强制 LocalOnly。
  • Draft-before-execution heuristic 可以把 write action 转换为 Proposal。

运行时效果：

  • 更安全的 tools、更少意外写入、更好的隐私策略、更贴合用户的行动节奏。

13.3 Observe 之后

输入：

  • Tool result、model result、user reaction、被拒绝/接受的 proposal、run outcome。

HS 工作：

  • LifeEventStore 规范化 observations。
  • SignalExtractor 找出 outcome、preference、rejection、success、failure、privacy 和 contradiction signals。

运行时效果：

  • Outcomes 成为可学习 evidence，而不是消失在 logs 中。

13.4 Reflect 期间

输入：

  • Run trace、observations、已选 heuristics、user feedback、result quality。

HS 工作：

  • EvidenceStore 更新 confidence、recency、opposition 和 negative evidence。
  • MaintenanceEngine 记录低质量 heuristic usage 或 conflict。

运行时效果：

  • Heuristics 根据实际效用提升或削弱。

13.5 Proposal 期间

输入：

  • Candidate heuristic/state/policy patches 和 evidence summary。

HS 工作：

  • LifeModelGovernor 分类风险、检查冲突、批处理低风险变更、附加 evidence 和 regression results，并创建 Proposals。

运行时效果：

  • 用户看到可治理、可解释的更新，而不是隐藏 personalization。

13.6 Replay / Regression 期间

输入：

  • New candidate heuristic、historical scenarios、accepted/rejected examples。

HS 工作：

  • RegressionSuite 验证 candidate 不违反已知 preferences、privacy policies 或 tool governance。
  • Replay 使用存储的 AgentSpec 和 ToolRuntime policy；HS 添加 scenario-level expected behavior checks。

运行时效果：

  • 新的学习更不容易破坏旧的已确认偏好。

  • 可用工具集和 side-effect class。
  • 当前 StateAssets 和适用的 PolicyAssets。
  • Candidate memory hits 和 evidence summaries。
  • Token budget 和 model route。

  + recency_or_state_validity * 0.10
  + priority * 0.10
  + regression_health * 0.10
  - conflict_penalty
  - prompt_pollution_penalty

硬过滤：

  • Privacy disallow。
  • Status 不是 active/trial。
  • Expired state。
  • Critical conflict unresolved。
  • Regression failed for this task class。
  • Token budget exhausted，除非 policy priority 是 high。

16. 治理设计

LifeModelGovernor 负责从 candidate 到 proposal 的转换。

决策阶段：

  1. Candidate intake：heuristic/state/policy patch 加 evidence links。
  2. Schema validation：required fields、paths、lifecycle state、owner/source。
  3. Risk classification：复用现有 LifeModel risk classifier，并扩展到 heuristics/policies。
  4. Evidence threshold：
  • 低风险 state：一个强 explicit signal 或重复弱 signals。
  • 中风险 preference/planning：多个 evidence points 或一个 explicit user statement。
  • 高风险 identity/values/privacy/long-term goals：即使 evidence 很强，也需要 explicit user confirmation。
  1. Conflict check：比较 affected paths、triggers、action effects 和 opposing evidence。
  2. Duplicate check：搜索相似 active heuristics，并提议 merge，而不是创建新 rule。
  3. Regression check：为中/高风险和 privacy/tool policies 运行相关 scenarios。
  4. Proposal shaping：产生简洁 explanation、before/after、evidence summary、risk、regression result 和 suggested action。
  5. Fatigue control：批处理相关低风险 proposals，推迟低置信度 changes，抑制反复被拒绝的 categories。
  6. Commit：已接受 proposals 在一个 transaction 中创建 HS assets 和 materialized view updates。

Governance 输出：

  • 创建 Proposal。
  • 合并进已有 Proposal。
  • 削弱/归档现有 asset。
  • 请求澄清。
  • 带 audit 丢弃 candidate。
  • 从重要的 accepted/rejected decision 创建 regression scenario。

17. 回归设计

Regression scenarios 是用户级行为测试，不只是代码测试。

Scenario 来源：

  • 用户明确说“做/不要做这个”。
  • 用户因行为错误拒绝 proposal。
  • 用户接受高风险 heuristic。
  • Privacy incident 或 near-miss。
  • Tool/action mistake。
  • 长期偏好经过时间确认。

Regression run 类型：

  • Deterministic policy check：“Sensitive topic must be LocalOnly.”
  • Selector check：“Draft-before-execution heuristic must be selected for external write.”
  • Prompt inclusion check：“No raw LifeModel appears in SummaryOnly view.”
  • Behavioral simulation：检查 model output 是否符合 must/must_not rules。
  • Replay-linked check：用 new heuristic 重新评估已存 run/action。

MVP 应从 deterministic checks 和 selector/prompt assertions 开始。由 LLM 判定的 behavioral simulation 是后续增强，因为它可能不稳定。

19. UI 与产品交互

目标 UI 不是 CRUD admin surface。它应该像一个个人操作系统的治理控制台。

必需界面：

  • Review Center：候选 heuristic/state/policy proposals，带 risk、evidence、regression 和“why now”。
  • Evidence drawer：显示 supporting 和 opposing evidence summaries、source type、recency 和 confidence。展示 raw source 需要用户操作。
  • Heuristic browser：active/trial/weakened/archived heuristics 按 domain 分组，而不是无尽 rule list。
  • Conflict queue：需要用户澄清的 contradictions。
  • Regression view：重要的个人行为测试、last run result 和 impacted candidates。
  • Materialized view inspector：展示 PromptStack 或 runtime packet 中包含了什么，同时不暴露 raw sensitive content。
  • Rollback/history：已接受 HS asset timeline、相关 proposal、patch 和 materialized view versions。
  • Maintenance inbox：compression、decay、stale rule 和 forgetting suggestions。

Review card 最少字段：

  • Candidate title 和 type。
  • Affected scope/path。
  • Risk 和 confirmation requirement。
  • Evidence summary 和 opposing evidence count。
  • Regression result。
  • Runtime effect。
  • Suggested action：accept、edit、reject、postpone、ask why、archive similar。

用户控制默认值：

  • High-risk proposals 绝不 batch accepted。
  • Low-risk proposals 可以批处理，但必须可检查。
  • “暂时拒绝类似项”应创建 negative evidence 和 cooldown。
  • “永远这样做”应创建带 high priority 的 user-authored heuristic proposal。

20. 与 Codex、Claude Code 和 Hermes 类自进化的对比

系统Memory / Evolution Unit相似性OpenLife 的差异
Codex / Claude Code project memoryProject instructions、working habits、coding preferences、repo conventions。Trace 和 experience 可以改善未来工作。范围是 project/workspace behavior，而不是个人生活身份；通常像 instructions，不是由用户治理的 life evidence。
OpenLife current memoryChat records、vector chunks、snapshots、state history、proposals。已经 local-first，并能支持 retrieval/proposals。需要 evidence graph、executable heuristics、regression、compression 和 field-level selection。
Hermes-like self-evolution由 trace 驱动优化 skills、prompts、tool descriptions 或 agent behavior。OpenLife 可以从 run traces 和 outcomes 学习。OpenLife 不能自主重写用户身份；用户主权和隐私要求更严格。
OpenLife LifeModel-HS由 trace 驱动优化个人 heuristics、context policy、privacy route、collaboration strategy 和 state continuity。使用 self-evolution patterns，但处于 governance 之下。强优势：在 chat/planning/tools 间提供个人连续性，并带 local-first audit。主要风险：错误学习会显得很个人，因此必须可逆。

OpenLife 优势：

  • Local-first personal data boundary。
  • 已有 ProposalStore、PatchStore、PromptStack、AgentRunEvent、ToolRuntime、ModelRouter 和 Privacy primitives。
  • 可以把个人上下文连接到真实行动治理，而不只是 chat memory。
  • User-governed negative evidence 和 regression 可以让学习比隐藏 memory 系统更安全。

OpenLife 缺口：

  • 还没有持久的 EvidenceStore/HeuristicStore。
  • 没有 selector quality metrics。
  • 没有 durable regression suite。
  • Legacy direct apply paths 仍需收敛。
  • UI 必须让 evidence 和 governance 易懂，且不压垮用户。

21. 迁移路径

迁移应该是增量式、兼容优先。不要重写当前 Agent framework。

Phase 0：ADR 和 Schema Freeze

  • 为 LifeModel source-of-truth shift 编写 ADR。
  • 冻结 LifeEvent、Signal、Evidence、Heuristic、StateAsset、PolicyAsset、RegressionScenario、MaterializedView 的 MVP schemas。
  • 定义 asset ids、versioning、privacy metadata 和 audit payload limits。
  • 将当前 YAML 定义为 lifemodel_yaml@compat。

Phase 1：EvidenceStore MVP

  • 添加 EvidenceStore 作为单独的 local store。
  • 将当前 MemoryEvidence 形状适配为持久 evidence。
  • 把 proposal rejection 记录为 negative evidence。
  • 把 evidence 链接到 memory ids、AgentRunEvent ids、proposals 和 affected paths。
  • 还不改变 runtime behavior。

Phase 2：HeuristicStore 和 Materializer MVP

  • 添加 HeuristicStore，使用上面的 schema。
  • 将 evolution_rules 迁移为 inactive/imported heuristics 或 materialized text。
  • 创建确定性的 YAML materializer，可以把 accepted state/preferences/heuristics 渲染到当前 LifeModel YAML fields。
  • 保留当前 LifeModelManager API，同时改变它的输入来源。

Phase 3：Selector MVP

  • 在 internal feature gate 或 design gate 后添加 HeuristicSelector 和 ContextSelector。
  • 第一次 runtime integration 只选择：
  • privacy-sensitive local model heuristic，
  • draft-before-execution heuristic，
  • low-energy planning heuristic。
  • 把已选 assets 渲染为 compact PromptBlocks 和 policy deltas。
  • 输出 metadata-only selection audit。

Phase 4：Governor 和 Regression MVP

  • 通过 LifeModelGovernor 路由候选 HS changes。
  • 为 privacy、draft-before-execution、low-energy planning 和 rejected reminders 添加 deterministic regression scenarios。
  • 中/高风险 heuristic promotion 需要 regression report。
  • 保持 ProposalStore 和 Review Center 作为面向用户的治理入口。

Phase 5：Compression 和 Maintenance MVP

  • 添加 maintenance scans：
  • duplicate heuristic clusters，
  • stale state assets，
  • low-quality heuristics，
  • conflict queue，
  • proposal fatigue signals。
  • Maintenance 创建 proposals，而不是 direct writes。

Phase 6：收敛 Legacy Paths

  • 把 run_micro_evolution direct apply behavior 转换为 proposal-only output。
  • 仅在 dev/test 中保留 allow_legacy_calibration_direct_apply，直到移除。
  • 审计所有 LifeModel writes：Builder、Calibration、Chat、Memory、Tool Permission、Proactive、Skill。
  • 要求 source audit，确认没有产品路径在 Governor/Proposal acceptance 外修改 canonical HS。

22. 第一版 MVP

第一版 MVP 应证明 HS 可以在不大范围重写的情况下改善一个真实 Agent run。

MVP 范围：

  • EvidenceStore 持久化。
  • HeuristicStore 持久化。
  • 三个 active heuristics：
  • 敏感主题优先使用本地模型，
  • 执行前先给草稿，
  • 低能量计划。
  • 一个 negative-evidence loop：
  • 被拒绝的提醒会降低主动提醒频率。
  • ContextSelector/HeuristicSelector 按 task 和 privacy 选择这些 heuristics。
  • Materializer 输出 compact runtime PromptBlock 和 policy deltas。
  • Review Center 可以 accept/reject/edit heuristic proposals。
  • RegressionSuite 对三个 active heuristics 有 deterministic checks。
  • YAML 仍是物化的兼容视图。

MVP 不应做：

  • 自主 identity rewrite。
  • 基于云的 raw LifeModel extraction。
  • 完整 automatic compression。
  • 跨所有 memories 的宽泛 semantic heuristic retrieval。
  • Auto-apply high-risk changes。
  • 替换现有 PromptStack 或 AgentRuntime foundations。
  • 构建复杂 expert-system rule editor。

MVP 验证：

  • 隐私敏感对话因为已选择的 HS policy 而路由为 LocalOnly。
  • 外部写入 action 因已选择的 HS heuristic 而变成 draft/proposal-first。
  • 低能量 state 导致更小的计划建议。
  • 被拒绝的提醒 proposals 减少未来 reminder candidates，或创建 cadence proposal。
  • Selection audit 展示 included/excluded heuristics，且不包含 raw sensitive payload。
  • Regression 捕获会违反 LocalOnly privacy 的 candidate。

26. 最终架构定位

LifeModel-HS 应作为增量架构层落地，而不是一次重写。当前 OpenLife Agent framework 已经拥有正确的治理主干：ProposalStore、PatchStore、AgentRunEvent、PromptStack、ToolRuntime、ExecutionSandbox、ModelRouter、ContextAssembler、MemoryStore、VectorStore 和 privacy policies。下一代 LifeModel 应使用这条主干，成为由用户治理的 Personal Heuristic System。

最重要的产品判断是克制。OpenLife 应从 traces 中学习，但它不应表现得好像每条 trace 都是真相。它应该把 life data 转化为 evidence，把 evidence 转化为 proposed heuristics，把 proposals 转化为 accepted assets，再把 accepted assets 转化为更好的 runtime behavior。用户仍然是所有者；HS 仍然可解释；materialized views 仍然可重建；Agent 变得更个人化，是因为它受到更多治理，而不是因为它更加隐藏。
